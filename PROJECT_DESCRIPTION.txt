DREAM LEAGUE FOOTBALL

An arcade, FIFA-style football game that runs in the browser, with a Serverpod back end for accounts, a persistent solo World Cup, live online matches, a server-refereed penalty duel, matchmaking and ratings.

Live: https://football.serverpod.space
API: https://football.api.serverpod.space
Code: https://github.com/hatif03/dream-league-football

WHAT THE APP DOES

Dream League Football is a full 11 v 11 football game drawn on an HTML canvas with a TV-style broadcast camera. It has the 48 nations of the 2026 World Cup, each with a real squad, kits and FIFA-style player ratings (pace, shooting, passing, dribbling, defending, physicality) that change how every player actually plays.

There are four ways to play:

1. Solo World Cup (signed in). Pick a nation and play the real 2026 draw: 12 groups, matchday by matchday. The server simulates the other games, builds the group tables with proper tie-breaks, draws the official Round-of-32 bracket (including the eight best third-placed teams) and takes you through the knockouts with extra time and a penalty shootout you take yourself. Every result is saved to your account and survives refreshes and new devices.

2. Play a friend online (signed in). One tap creates a room. Share the 5-character code, a link, the phone share sheet or a QR code, or invite a friend from your friends list. Both players see joins, leaves, nation picks and readiness live, then a 3-2-1 count-in starts a match. One browser runs the simulation and streams it to the other; both players sign the final score, and the result and head-to-head record are stored. Leaving a match tells the opponent within about a tenth of a second and the server marks the match abandoned.

3. Penalty duel (signed in). Five penalties each, then sudden death, against another player found through matchmaking or a room code. Every kick both players choose one of six zones in secret (shooter and keeper) and the Serverpod server draws the result, so nothing runs in a browser that a player could tamper with. Ratings (Elo) move after every finished game.

4. Practice (no account needed). An open pitch with a keeper, no clock and no pressure, plus a penalty shootout against the CPU.

Also: an 11 v 11 friendly against the CPU, an interactive tutorial, a club crest and kit editor, 24 avatars, 14 achievements, a daily challenge with a streak, a global leaderboard by rating or points, quick chat in online matches, shareable result links with a picture preview, goal replays, commentary captions, a stadium crowd, added time, settings that follow your account, and an installable app.

Around the matches there are friends, blocks, invites, lobby chat, player reports, presence dots, a record with head-to-head, and account deletion. The football rules are real: offside, throw-ins, corners, goal kicks, fouls with free kicks and a four-man wall, penalties, yellow and red cards, extra time and shootouts, three CPU difficulty levels, a goalkeeper with dives and handling rules, charged shots and passes, through balls, slide tackles and contain.

It plays on keyboard (the FIFA classic arrows layout or the EA FC WASD layout), controller (the EA FC layout) or touch, with every input rebindable. The menus are console-style (arrows or D-pad, Enter/A, Esc/B) and the footer shows the buttons of the device you used last. On phones matches run in landscape with on-screen controls.

HOW IT USES SERVERPOD

The whole back end is one Serverpod 4.0.3 project (Dart, PostgreSQL) in the football/ folder, deployed on Serverpod Cloud as project "football".

- Authentication: Serverpod's email identity provider with the JWT token manager. Sign-up uses an emailed verification code (sent through Serverpod Cloud's email service, branded "Dream League Football"), then a unique display name. Access tokens last 10 minutes and are refreshed by the web app.
- Endpoints: 16 endpoint classes: profile, tournament, lobby, friendMatch, matchmaking, penalty, challenges, share, rankings, friends, chat, report, liveOps and admin, plus the generated auth endpoints. Every game endpoint requires login. The web app calls them as plain JSON (POST /<endpoint>/<method> with a bearer token).
- Database and models: 15 game tables defined as .spy.yaml models (profiles with a rating, tournaments and fixtures, lobbies, friend matches, penalty kicks, the matchmaking queue, shared results, friendships, blocks, invites, chat, reports, audit log, maintenance switch) with 10 versioned migrations applied at boot. Local development and tests use Serverpod's embedded PostgreSQL, so Docker is not needed.
- Trust between two players: the match runs in one player's browser, so the server makes the result trustworthy. Each player posts a signed claim of the score; the server stores the match only when both claims are identical, written in a transaction with a row lock (LockMode.forUpdate) so two near-simultaneous claims never overwrite each other. Mismatches, one-sided claims and abandoned matches are handled by explicit rules and unit tests.
- The server as referee: the penalty duel is played on Serverpod. Both players post a secret zone (0 to 5) per kick; under a row lock the server draws the outcome with secure randomness, opens the next kick or finishes the duel and applies Elo in the same transaction. The other player's choice is never sent to a client before the kick is settled.
- Matchmaking: a queue table and an endpoint that pairs two players of the same mode and build by rating, with a window that widens the longer both wait, blocks respected, and a transaction with row locks so nobody is paired twice.
- Future calls: a recurring nightly maintenance job on a cron schedule (closes idle rooms, voids stuck matches, prunes the queue and old chat) and one scheduled timeout per penalty kick, so a duel finishes even if both players close their tabs.
- Live push: a /live WebSocket route (JWT in the first frame) and an in-memory hub that tells the right players when friends, rooms, chat, duels or the queue change, replacing most polling.
- Cloud storage and share pages: result pictures go to Serverpod Cloud public storage, and a /r/<id> web route serves an Open Graph preview page so a shared score shows as a picture in chat apps.
- Peer-to-peer introduction: the WebRTC offer and answer are stored on the FriendMatch row, so Serverpod is the signalling channel between the two browsers.
- Relay fallback: a Relic web-server route, /relay/<matchId>, is a WebSocket that authenticates both players with their JWT and forwards match frames when a direct connection fails.
- Web hosting: the same Serverpod web server serves the built web app with a single-page fallback, so the site, the relay and the API need no CORS or cookie setup.
- Solo World Cup logic on the server: group tables with head-to-head tie-breaks, matchday-limited simulation of the other games, the official 2026 knockout bracket with third-placed team assignment (tested against all 495 possible combinations), and idempotent result submission.
- Social and operations: friends by exact name, blocks, invites, presence (lastSeenAt), rate limiting, a profanity mask, a maintenance switch, suspensions and operator endpoints gated by the adminUserIds password.
- Serverpod Cloud: one-command deploys with scloud, managed database, TLS and email, and secrets set with scloud password.
- Tests: 31 dart tests (group logic, the bracket, result-claim resolution, shootout rules, Elo, the daily challenge, and serverpod_test integration tests that call the real matchmaking and duel endpoints), plus HTTP smoke tests and real-browser end-to-end tests that drive the app against the local Serverpod server.

HOW IT RELATES TO FLUTTER

To be accurate: the user interface is not written in Flutter. The game and every screen are a React 19 / TypeScript web app (Vite, Tailwind) with a hand-written canvas game engine, chosen because the match needs a real-time canvas renderer and runs in any browser, including phones, with no install.

Flutter is part of the project as the Dart toolchain behind Serverpod: the Serverpod server is Dart and builds and runs on the Flutter SDK's Dart, the project is a Dart workspace (football_server and football_client), and Serverpod generates a Dart client package (football_client) from the server's models and endpoints. The web app talks to the same endpoints with plain JSON instead of that generated client, so football_client is generated and kept up to date but not used by the UI. A Flutter front end could be added on top of the same server without changing it.

HOW TO TRY IT

1. Open https://football.serverpod.space. Practice works immediately without an account.
2. To use the World Cup or play a friend, create an account (an emailed code confirms your address), choose a player name, and pick a nation.
3. For an online match, one player opens Online, creates a room and shares the code or link; the other opens it on any device. Both choose different nations, press "I'm ready", and play.

Run it yourself (README.md and docs/DEVELOPMENT.md have the details):
  npm install
  npm run dev                                   (web app on :5173)
  cd football/football_server
  cp config/passwords.example.yaml config/passwords.yaml   (fill in secrets)
  dart bin/main.dart --apply-migrations --role monolith    (server on :8080, no Docker needed)

STATE OF THE SUBMISSION

Working and verified: the live site loads over the Serverpod web host with working deep links and cross-origin API calls; the 31 server tests pass; the HTTP smoke tests pass (including matchmaking, a whole duel, the live socket and the share page); and real-browser tests pass for sign-up through a World Cup match, a knockout game with extra time and a penalty shootout, controller and touch input, both keyboard layouts, two real browsers playing a friend match end to end (direct WebRTC, relay fallback, leaving, tab-close abandonment and invites), two browsers meeting through matchmaking and playing a penalty duel, and the replay, commentary, added time and share-link features.

Known limits, stated plainly: production sign-up sends a real email, so the live sign-up flow was not scripted against the deployed site (it is tested locally, where the code is printed to the console); layouts were checked at emulated phone sizes, not on physical phones; a full match over the production relay has not been timed; the 11 v 11 online match is still simulated by the host (so a modified host could cheat it, which is why the penalty duel is refereed by the server); the live socket keeps its connections in one server instance's memory; and there is no spectating yet.
